# 软件过程管理与工程伦理 · 课程实践项目（PJ）任务书

## 一、项目说明

本学期实践项目为校园资源服务平台。以自习座位预约为核心，向校园空间的申请与维护两端延伸。

本项目要求使用 AI 编程助手（智能代理，如 Codex、Qoder 等）开发。考查重点不是功能做了多少，而是能否有条理地使用智能代理开发出一个可交付的系统。在评价时，一个经过思考和规划的开发过程优于功能的堆叠。

技术栈自选，建议选择企业级的方案；不提供初始化代码或脚手架。

## 二、分组与模块

### 分组

- 全班按 6 人左右组成一个项目组，每组独立完成一套完整系统。
- 每个项目组内分为至少 3 个模块组，各认领一个模块。
- 每个项目组独占一套开发、测试、生产环境，组内各模块组共用本组环境。

项目组是环境与评级的单位，模块组是开发与分工的单位。

### 模块划分

| 模块 | 名称 | 主要功能 |
|---|---|---|
| M1 | 自习座位预约 | 按条件搜索座位、预约时段、签到、违约记录、历史复用 |
| M2 | 整教室预约与审批 | 权限门槛、申请提交、多级审批（通过／驳回）、超时自动撤销 |
| M3 | 物业报修工单 | 故障上报、派单、维修中状态、超时升级、完工验收与评价 |
| D | 公共层 | 基于 RBAC 的身份与权限、空间与座位主数据、通知服务、操作审计等 |

公共层 D 的归属由项目组自行决定（可由某一模块组承担，或按子域拆分）。决定时须权衡工作量均衡、契约治理、故障责任归属等因素，并形成书面决策记录：说明采用什么方案、考虑了什么、依据是什么、如何达成组内一致。

M1 部分的内容见附件 1。M2、M3 和 D 根据自己的理解，通过与 AI 交互完成细化的需求。

### 跨模块集成

以下两条状态写回链路与一条座位状态追溯要求是跨模块集成的示例，各组须讨论是否需要补充其他跨模块集成点。

- **M3 → M1：**某自习室存在“维修中”的报修工单时，该室全部座位自动从可预约列表下架；工单验收通过后自动恢复。
- **M2 → M1：**整教室预约审批通过后，该室在预约时段内的全部座位被占用，不接受个人预约；审批驳回或超时撤销后回滚。
- M1 的座位状态必须记录写入来源（M1 自身预约／M2 审批占用／M3 报修下架），供追溯与验收。

## 三、考核重点

### 人机协作能力

考查人与 AI 如何分工、如何验证、如何约束。需要做到：

| 方面 | 要求 |
|---|---|
| 规则 | 项目约定以机器可读形式固化并随代码版本管理（如 AGENTS.md、spec），不是每次对话重复交代。AI 不需要被反复告知同一件事。 |
| 任务委派 | 交给 AI 的任务有明确范围、约束与验收标准；先出方案再实现。 |
| 质量保证 | 能说明 AI 生成代码的质量隐患与应对方式。 |

### 工程化实践

#### 版本管理

从第一次提交开始，版本管理贯穿项目全程；提交历史是开发过程的主要证据，AI 对话记录不能替代。

| 方面 | 要求 |
|---|---|
| 产物覆盖 | 代码、项目规则文件、需求与决策记录、迁移脚本、流水线配置等均纳入版本管理，随项目进展持续提交，不等到最后集中提交。 |
| 提交质量 | 提交说明能对应任务或需求，讲清做了什么、为什么；AI 生成的变更须经人工验收后提交，避免出现无法审查的大批量变更。 |
| 分支与合并 | 分支与合并策略明确；变更经合并请求评审后合并；代码冲突由人处理，不得交由 AI 自行合并。 |
| 版本标记 | 部署版本有可追溯的标记（tag）；能从部署回溯到对应提交，并说明每次发布包含哪些变更。 |

#### 交付流水线

尽可能早地自动部署到测试服务器和生产环境。

| 环节 | 要求 |
|---|---|
| 构建 | 提交与合并请求自动触发构建；测试失败则后续阶段不执行。 |
| 质量门禁 | 测试不过不能合并；跨模块变更、公共层变更、schema 变更须经组内评审。 |
| 测试环境 | 流水线自动部署，无需人工干预；一次部署覆盖本组交付的所有模块。 |
| 生产环境 | 需人工审批后发布；应可回滚；能说明当前运行的是哪个版本。 |
| 发布协调 | 本组独占生产环境，不受其他项目组影响；但组内各模块的发布顺序须协调。 |

#### 数据演进

在迭代过程中持续演进数据库 schema 与初始化数据。

| 方面 | 要求 |
|---|---|
| Schema 迁移 | 结构变更以版本化迁移脚本提交，可重复执行；禁止手工改库；从空库到最新版本可一次性重放。 |
| 种子数据 | 脚本化、幂等；与业务数据分离；随结构同步更新。 |

请约定部署窗口或等效机制，避免某模块正在部署时其他模块的集成测试误报失败。

#### 其他要求

- 需求基线明确且可追踪：每条需求能指出对应的实现与验证方式；未完成的部分明确记录，而不是从清单中消失。缺少验收标准的需求不算完整的需求。
- 测试必须确实验证了行为：AI 容易生成“看起来完整但什么都没测”的测试（断言常量、覆盖空分支、mock 掉被测逻辑本身）。验证手段：故意破坏实现，观察测试是否失败。
- 基础设施尽量脚本化，不依赖人工在服务器上逐条操作（推荐 Docker 等容器化方式与相关配置）。

#### 架构与决策

理解和评估 AI 给出的候选方案，而非直接接受 AI 首次给出的方案。

另设课程论文（个人），结合本组实践讨论过程管理与工程伦理问题。

## 四、工程伦理的融入

本课程同时考查工程伦理。本项目要求各组在开发过程中，结合本组系统思考如何把工程伦理融入项目的各个阶段，而不是项目结束后补写；每位成员最后将这部分内容写入个人提交的课程论文。

### 个人报告中的体现

每位成员在课程论文中结合本人参与的工作，写出自己的分析与思考：本组识别或遇到了哪些伦理问题、如何应对、还有哪些存疑之处。分析应基于本组开发过程中的真实情况。

## 五、附加项：自然语言会话驱动的业务代理

在完成上述要求的基础上，额外实现一个以自然语言会话驱动业务操作的代理（Agent），通过它可以完成本系统的主要操作。本项为附加要求，不影响前述任何要求的达成。

### 业务范围

会话应能覆盖三个业务模块的主要操作：

| 模块 | 覆盖的操作示例 |
|---|---|
| M1 自习座位预约 | 查询可用座位、发起预约、查询历史记录 |
| M2 整教室预约与审批 | 提交整教室预约申请、查询申请状态、撤销申请 |
| M3 物业报修工单 | 上报故障、查询工单状态、取消工单 |

上面仅仅是示例，如果可能，尽可能泛化。

### 实现方式

本项目与课程个人 Lab 所分析的 DeepSeek Harness（Everything is a Plugin.）是同一技术对象，因此建议以插件形式实现该代理，作为 DSH 的插件接入：

- 代理的业务能力通过各模块的公开接口调用，不与模块内部耦合。
- 插件的安装、配置与调用过程纳入本项目的部署流水线。

### 检验点

这个附加项的真正价值在于检验前面各模块的集成是否真的可用，因此关注以下几点：

| 检验点 | 说明 |
|---|---|
| 真实调用而非模拟 | 必须通过各模块的公开接口调用业务能力，不得直接访问其他模块的数据库或内部实现。若为方便而在代理中重新实现业务逻辑，本项视为未完成。 |
| 不确定性处理 | 涉及操作意图不明确时，代理应追问而非擅自执行。比如“我要预约一间教室”，Agent 会追问时间和区域。 |

## 六、评审节点

不设定统一的阶段完成时间，各项目组自行安排节奏。

| 节点 | 提交内容 |
|---|---|
| 项目启动 | 分组完成；各模块组认领模块；组内分工；公共层归属方案与决策记录。 |
| 第一次 Review | 需求基线；任务分解与依赖关系；架构搭建和第一次迭代功能；项目级规则文件与 AI 协作方式；风险识别。 |
| 第二次 Review | 主功能完成且集成链路打通；集成测试通过；schema 迁移在流水线中自动执行；从提交到部署的全流程可演示；质量保证手段。 |
| 期末展示 | 完整功能演示 + 人机协作过程与工程实践说明。 |

## 七、期末展示要求

展示材料中应包含以下内容的实际演示（而非截图）：

1. 从一个全新环境开始，通过流水线完成部署。
2. 提交一次变更，观察自动触发构建与测试。
3. 执行一次包含 schema 变更的部署，说明数据如何演化（可以从历史中挑选）。
4. 演示一次生产环境发布与回退。
5. 演示一条跨模块链路：模块 A 通过网络调用模块 B，展示状态写回效果。

实现了第五节附加项的，还需演示一次自然语言会话驱动的业务操作。

## 八、不作限制的事项

以下方面不作要求，由各项目组自行决定：需求文档的组织方式（用户故事、用例、原型等均可）、进度安排与技术选型、AI 工具的选择、公共层的承担方案。

不作限制不等于不作要求。需求应当可追踪、进度应当可查看、决策应当有依据，AI 的输出应当可验证。

## 附件 1：自习室预约系统说明

### 系统概述

为了方便学生自习，学校开放了一批自习室。自习室中的座位利用率不高，经常出现一座难求，同时又有书包占座、人却不在的情况。为了提升座位的利用率和周转率，学校一方面考虑动态调整自习室的数量，另一方面也希望采用信息技术手段提升座位的利用率。

### 关于系统学生端的实现

学生端可以选择在手机上实现（微信小程序）或在 Web 浏览器（Web 应用）上实现。

### 基本概念

- **自习室：**用于学生自习的场所，包括普通教室、图书馆的专用自习室以及其他区域的自习场地。自习室可以是学校统一管理的，也可以是属于院系的。对于属于院系的自习室只对本院系的同学开放。自习室的登记、注销、可用性维护由管理员统一管理。
- **自习座位：**自习室内登记在册的座位。有唯一编号，可按需预定。座位的登记、注销、可用性由管理员统一管理。

### 具体需求

1. **配置管理：**通过自习座位预约系统，系统管理员可以管理所有系统配置、角色、权限。
   1. 可以设定可用的自习室、自习室开放时间。
   2. 可以设定新的角色权限，例如，教室管理员（管理自习室及座位）、运营管理员（查看统计数据和预约情况）等，每个角色拥有自己的权限以及能够管理或参与的内容。
2. **预约功能：**学生则可以查看可用自习室，并预约自习时间。为了提高座位利用率并考虑减少学生连续学习造成的疲劳，每次预约均以整点小时为单位，最多一次性预约 4 小时（系统参数可调）。
3. **签到功能：**学生按预约到达座位后，需要有签到功能。自习教室屏幕上需要每天会显示一个动态的与教室关联的编码或者二维码，如果是通过 Web 应用签到，则录入编码，如果是微信签到，则扫描二维码。
4. **提醒与违约记录：**在预约时间之前 15 分钟会有推送（邮件推送或微信服务号推送等）提醒；在预约时间之后 10 分钟如果还未签到，则会再次提醒；预约时间 15 分钟后如果还未签到，则自动取消预约、释放座位，并提醒学生，同时后台记录一次违约。
5. **搜索与历史查询：**为了便于使用，学生需要能够方便地对所需的座位进行搜索，也可以查看历史预定并再次预定该座位。
6. **运营管理：**管理员通过查看自习室和座位的预约情况来调整管理策略，提升资源利用率。
7. **座位特殊标记：**为了便于学生在线资料获取和学习，靠近固定插座或者移动导轨插座的座位有会有特殊标记，学生也可以在搜索时作为条件，以便学生携带电子设备使用。
