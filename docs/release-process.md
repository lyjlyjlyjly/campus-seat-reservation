# 发布与部署安排

当前范围是本机运行和一个 GitHub Actions 检查 job。两天计划明确延期服务器部署与生产发布；仓库尚无 `scripts/bootstrap.sh`、`scripts/deploy.sh` 或 deploy job，不能据本文宣称已具备自动交付能力。运行方式见 [README](../README.md)，流水线现状见 [CI 规范](ci.md)。

## 后续交付任务

| 任务 | 负责人角色 | 完成证据 |
|---|---|---|
| 服务器、SSH 和测试/生产隔离 | G3 基础设施负责人，G2 发布负责人 | 实际环境、目录、端口、独立 SQLite 路径；凭据仅在服务器或 Secrets |
| 首次环境准备脚本 | G3 | `scripts/bootstrap.sh` 能从目标服务器初始环境准备 Python 和服务目录 |
| 测试自动部署 | G3 | main 检查成功后执行 deploy-test，健康检查能确认新 commit |
| 生产审批与 tag 发布 | G2 | 人工批准指定 tag 后部署；`/version` 能追溯实际版本 |
| 数据备份和回滚 | G2/G3、各模块 | 备份可用、恢复演练成功、schema 兼容性有记录 |
| 发布窗口与模块协调 | 发布负责人、三组代表 | 真实约定的时间段、参与人、验收和失败处理记录 |

具体服务器和发布窗口尚未提供，不填虚构地址或日期。后续先写 spec 并确认跨组影响，再实现以上脚本和流程。

## 后续发布验收口径

发布顺序应包含：确定待发布 tag/commit、备份目标 SQLite、更新单体代码、应用迁移、重启服务、验证 `/health` 和 `/version`、按本次变更验收业务。生产前须有人的批准，测试环境可在检查通过后自动部署。

回滚先判断旧代码是否兼容新 schema；不能只切 tag 就假定数据安全。需要恢复数据库时由负责人依据备份、维护窗口和期间数据变化明确决定，记录可能丢失的数据及处理方式。成功与失败都留下真实 tag/commit、操作人、时间和验收证据。

计划版本沿用 `v0.1.0`（Review 1）、`v0.2.0`（Review 2）、`v1.0.0`（期末）；这些是计划标签，目前并未创建或发布。业务功能、部署和回滚是否完成分别追踪在 [需求基线](requirements.md)。
