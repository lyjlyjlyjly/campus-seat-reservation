# 需求基线与实现追踪

基线日期：2026-10-20。来源：[课程任务书](Pj-任务书.md)、[PJ 计划书](PJ-计划书.md)。本文件维护需求状态、首轮实现范围与证据；集成顺序和公共依赖见 [架构](architecture.md)。

当前只有 [SPEC-000 仓库骨架](specs/000-repository-bootstrap.md)，以下业务需求均未交付。`app/m1/`、`app/m2/`、`app/m3/`、`app/d/` 是预留实现目录，不能作为需求已完成的证据。表中“待开发”不是“已实现”；完成时必须把实现、实际测试和 PR 链接填入证据列。

## 本轮口径

- 目标是三条最小业务链：M1 搜索→预约；M2 登录→申请→一级审批；M3 文字报修→派单→维修中。
- “部分待开发”表示只安排下表注明的子范围，其余部分仍保留。统一延期原因 R1：首轮仅两天，先完成主路径，后续按 Review 2 计划补充；任何删减仍需确认课程要求。
- 全部验收条件以 Given–When–Then 描述。表内延期需求的条件是后续候选验收，涉及通知/定时等未决范围需先确认后细化，不能直接据此扩展本轮。
- M2 角色口径待短会确认：长期计划限定教师、学生组织负责人，两天计划使用学生演示账号；G2 须明确哪个演示角色拥有 `room:apply`，不得默认所有学生均可申请。

## 更新规则与风险

需求范围改变须保留原 ID 和未完成部分，并写明原因、确认依据和后续安排。完成时将“实现 / 测试 / PR”填为可点击证据，部分通过不得标成全部完成。G1 汇总本文件，各组维护自己需求的事实。

| 风险 | 应对 | 当前责任 |
|---|---|---|
| 公共身份/字段未冻结 | 优先执行两天计划任务 1；不在业务分支各自发明一套 | 三组代表、项目负责人 |
| 骨架被当成业务完成 | 逐项维护以上证据列；Review 用真实业务链验收 | 各组 |
| AI 的测试只覆盖常量或模拟逻辑 | 审查可观察结果，补拒绝路径及故意破坏实验 | 实现人、评审人 |
| 两天内不断扩范围 | 延期项保持可见，新想法先记录后评审 | 项目负责人 |
| 服务器未准备而宣称交付完成 | 本轮明确本机与 CI 范围；后续排部署任务 | 发布/基础设施负责人 |
