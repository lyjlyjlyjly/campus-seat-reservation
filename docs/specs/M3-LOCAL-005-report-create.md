## 方案与选择

| 方案 | 取舍 |
|---|---|
| 路由内逐项查询后调用原有独立连接 create_repair_order | 文件少，但校验与写入分离，有权限撤销竞态；不采用 |
| 小型身份适配入口 + 请求模型 + 创建服务 + 同连接写入（采用） | 事务边界明确；真实身份接入集中，服务内只读共享身份/授权/房间表 |

创建服务使用 `BEGIN IMMEDIATE`，同连接检查 ACTIVE、真实 repair:report 授权、房间存在性，再插入并读取结果；提交成功后才返回 201。保留原 repository 公开调用兼容性，抽出接收连接的写入函数，不自动初始化。列表与创建共用房间读取规则，停借资产允许报修。

认证按固定 G2 `current_user(request)` 契约懒加载，缺少指定模块才返回 503；内部依赖损坏/未知异常不伪装成未就绪。只使用服务端返回的用户 ID，权限在数据库事务内复核。错误适配使用 M3 专属 APIRoute，不安装全局异常处理器，不影响其他模块或未来共享处理器。

使用现有 Pydantic 请求模型，严格类型、禁止额外字段；分类/描述 strip 后校验。描述按 Unicode 码点计数，拒绝 NUL；无法编码为 UTF-8 的孤立代理码点也返回 422，避免进入 SQLite 后成为内部编码异常。PR #2 尚未合入，当前最小规范化留在模型，未来只替换此入口，不扩大 PR #2 宽松约定。

页面复用公共 CSS 和现有静态挂载。原生 JS 使用 textContent 展示、按码点计数且不设 UTF-16 maxlength。请求结果不明时不重发，锁定再次提交并提示先核实；本接口不承诺幂等。仅认证返回 401 且当前应用确实挂载登录页时展示登录链接，不自动跳转。

| Given | When | Then |
|---|---|---|
| 服务端身份及真实临时库 ACTIVE 用户/授权/房间 | 提交合法三字段 JSON | 201；新连接读到本人 REPORTED、服务端时间，四个派单字段 NULL |
