# Agent Note: ADR-001 公共层归属

Status: proposed — 分工来自计划，等待三组确认和会议记录

Date: 2026-10-20
Owner: 项目负责人协调 G1、G2、G3
References: [任务规格](../../../../docs/specs/000-repository-bootstrap.md)、[需求基线](../../../../docs/requirements.md)

## Problem

六人分成三个业务组；公共层包含身份、权限、空间、初始化、反馈和审计。如果无人统一负责，模块可能形成不同的用户、角色和座位模型。M1 的预约约束最多，后续还将接收跨模块状态写回，公共工作不能平均按目录数量分配。

## Proposal

G1 负责 M1。G2 负责 M2，兼认证、RBAC、审计及登录页面和公共布局。G3 负责 M3，兼空间/座位主数据、迁移与种子汇总及即时反馈约定。三组页面共同使用即时反馈约定，G3 不包办所有业务页面。

公共变更由负责人协调，至少一名其他组成员评审。当前 A–F 只是计划中的角色占位，真实 GitHub 账号、人员认领、会议时间和表决结果仍待记录。

## Alternatives considered

| 方案 | 收益 | 代价 / 取舍 |
|---|---|---|
| 公共层按子域分给 G2/G3 | 减轻 M1 负担，仍有明确目录归属 | 两组必须共同冻结身份与主数据契约；作为当前提案 |
| 全部公共层交给一个组 | 责任入口单一 | 单组承担明显更多前置依赖 |
| 各业务组各写一份公共层 | 各组可以独立推进 | 用户、权限和空间模型重复，集成时易产生冲突 |
| 另设第四个公共组 | 公共治理集中 | 与六人三个业务组的配置不匹配 |

AI 初始建议：沿用两份计划中的子域分工。组内最终选择：尚待确认；当前目录仅使该提案可审阅，不作为投票完成的证据。

## Acceptance criteria

- Given 三组讨论分工，When 采纳方案，Then 会议记录包含实际参会人、结论和未决项，Note 链接该记录。
- Given 公共层代码改动，When 创建 PR，Then 能按目录找到负责人，并由受影响的另一组评审。
- Given 真实成员账号已提供，When 更新 CODEOWNERS，Then 规则与已确认分工一致。

## Risks

G2 的登录可能阻塞其他组；G3 的主数据和种子也属于前置依赖。两天计划的任务 1 应优先冻结接口与字段。审计在本轮延期，不得因为目录已经存在就标记 D-R05 完成。
